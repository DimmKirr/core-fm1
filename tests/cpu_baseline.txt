FM Lab -- audio ISR load, measured on the device
================================================

How
---
Flash the build, select a voice, press FX to clear PK, then:

    python tools/load_test.py            # 1, 2, 4, 6, 8 notes held, 10 s each

Read CPU (smoothed) and PK (worst single block) off the bottom of the screen.
Both are a percentage of the budget: the ISR must render HALF_FRAMES (256) before
the DMA plays them, which at FS 44100 is 5804 us. Over 100 % means it cannot keep up.

Measured
--------
2026-10-11, FM-1 hardware, FM-1_970, DX_LG_N 6, NV 8, voice 6 BRASS
(algorithm 22, all six operators sounding, four carriers, sustains while held --
the worst case among the factory voices):

    8 notes held     CPU ~26 %     PK 33 %

So roughly 3.3 % of the ISR budget per six-operator voice, and eight voices leave
about three quarters of the budget unused. No red line, no shed voices, no glitching.

This agrees with sloopDX, which measured 65 % for 14 voices that each also carry a
filter and an amp envelope (14 x 3.3 % = 46 % for the FM alone, the rest theirs).

Editing while it sounds (step 3)
--------------------------------
Same day, same voice, with the parameter editor in. A knob detent copies the 156
bytes, publishes them, and makes the ISR run dx_update over every sounding voice,
so the worst case is eight notes held while a knob is spun as fast as it will go:

    8 notes held                     CPU 26 %   PK 32 %
    8 notes + LEVEL spun hard        CPU 26 %   PK 32 %
    8 notes + ALGORITHM spun hard    CPU 26 %   PK 33 %

Editing is free, to within the resolution of the meter. That is the point of
dx_update: it recomputes the operator rates and levels but leaves every phase and
envelope where it stood, so it is a few hundred cycles per voice and never a
retrigger. Spinning ALGORITHM costs the extra 1 % because it also re-reads which
operators are carriers.

Drawing while it sounds (step 4)
--------------------------------
Same day, same voice. Step 4 added the two live drawings and raised CV_MAX from
240x64 to 240x136, so this is the measurement that matters most:

    8 notes held, HOME page        CPU 26 %   PK 33 %
    8 notes held, ENVELOPE page    CPU 26 %   PK 33 %

Nothing moved, and nothing clicked. HOME re-blits only the six operator boxes
(~1.3 k pixels each) about 16 times a second; ENVELOPE redraws the whole 240x72
graph at the same rate and is the more expensive of the two, yet neither is
visible in the meter.

The reason is structural rather than lucky: all drawing happens in app_main, and
CPU/PK measure the audio ISR, which pre-empts it. Painting can only hurt the
audio by stealing memory bandwidth from the ISR or by holding it off, and a 1 %
move in PK is the size of that effect. The headroom the UI actually spends is the
main loop's, which has no deadline. The number to watch would be the frame rate,
not CPU -- and the drawing stays smooth.

Switching operators off while it sounds (step 5)
------------------------------------------------
8 notes held, operators switched off and soloed, sides flipped: CPU 26 PK 32.
Unchanged again, and for a simpler reason than step 4's: the mute mask is applied
in patch_publish, which runs once per changed parameter, not once per block. By
the time the ISR sees the voice it is an ordinary 156 bytes with some zeroes in
it, and dx_update costs the same whatever those bytes say. A switched-off
operator still runs -- its envelope floors at 16<<16 and it multiplies through at
nothing. Not free in principle, but free in the meter, and keeping it running is
what lets it come back mid-note without a click.

Saving, and .syx in and out (step 6)
------------------------------------
2026-10-11, same hardware, voice 6 BRASS, 8 notes held: CPU 26 PK 33. Unchanged.
A bank sent in and dumped back out while the chord sounded did not move either
number. The bank costs nothing per block -- it is 4 KiB of RAM the ISR never
reads, and load_voice touches the voice once, the same as turning PRESETS always
did.

Two things here are not free, and both are deliberate:

  - bank_store writes flash: two fl_erase4k calls at roughly 50 ms each with
    interrupts off, so about 100 ms of silence on a save. Nothing can be done
    about that -- the chip cannot fetch instructions from flash while it is being
    programmed -- so it is made visible instead: it happens only on a SAVE you
    pressed twice, and the screen says SAVED.
  - a bulk dump arriving is 4102 bytes assembled in the USB ISR a few at a time,
    then unpacked in the main loop. The main loop has no deadline, and the per-
    byte work in the ISR is a bounds check and a store. PK did not move.

A note for anyone writing their own librarian: sending a 4104-byte dump back is
fine on the device -- ota_wire_send queues 3 bytes per USB-MIDI packet and the
2 kHz TIMER5 ISR drains 16 packets a go, so the whole bank clears in well under
100 ms -- but RtMidi on Windows gives WinMM only 4 x 1024 bytes of SysEx input
buffer and drops a longer message with no error at all. The device says BANK SENT
and nothing arrives. tools/syx.py talks to WinMM directly for that reason.

RAM went from 17064 to 24712 bytes of 98304: sx_frame grew 640 -> 4160 to hold a
bulk dump, and bankmsg is 4104. Image 103112 -> 105484 of 581564. Both still
comfortable.

The panel tweaks
----------------
Image 105484 -> 105988 -> 106904 of 581564, RAM 24712 -> 24728 -> 24760 of
98304, over the two panel commits. Nothing in either touches the audio path per
sample, and the measured 26 % / PK 33 % on voice 6 BRASS with eight voices is
unchanged.

Mono mode uses one voice, so the figure there is roughly an eighth of the poly
one. It is not a number to tune against: measure in poly, which is the worst
case.

The spectrum
------------
Image 106904 -> 107516 -> 109464 of 581564, RAM 24760 -> 24776 -> 30648 of 98304,
over the naming and spectrum commits. The spectrum's RAM is the ring, the
twiddles, the window and the two column arrays, 5874 bytes; its 8 KB of FFT
workspace is in the pool, 65280 -> 73472 of 344064.

The measured figure on voice 6 BRASS with eight voices is 26 % / PK 33 % with
the spectrum screen up and playing -- unchanged. That is not quite the result it
looks like, because the meter only times app_audio: the only thing the analyser
adds to the ISR is sp_feed, a store and an increment, and the transform itself
runs in the main loop where the meter cannot see it.

So the cost of this screen has to be judged the other way, by whether the panel
still answers. A 1024-point FFT is 5120 butterflies, once every 60 ms, which is
small; the thing that is not small is the blit. The plot is 240 x 136 and it goes
to the screen sixteen times a second, by far the most screen traffic this
firmware has ever pushed. lcd_blit is asynchronous and cv_begin waits on it, so
the transform for the next frame overlaps the last frame's DMA -- but if the DMA
ever took longer than the frame, the main loop would stall in cv_begin and the
keys would go with it. On the hardware it does not: nothing feels slow. If a
later change makes it feel slow, the first thing to try is drawing it less often.

To measure anything that you cannot watch the meter during, press FX to clear PK,
do the thing, then go to GLOBAL and read it: PK holds until it is cleared, and
GLOBAL is the only page the meter is on now.

The knob legend
---------------
image 109668 B, RAM .data+.bss 30648 B, pool 73472 B. 28 bytes of image over the
spectrum build, no RAM at all: the names are const strings in the four parameter
tables and the strip is one 240x16 canvas blit.

It is drawn once, from the same block that clears the screen on a page or bank
change, because that is exactly when its contents change -- not on the 60 ms tick.
So it costs nothing while you are playing. The audio ISR cannot see it either
way; the meter read the same 26 % / PK 33 % after it as before.

Six characters is the width of a cell (FONT_S advances 8, cells are 60 wide, and
3 px of margin either side of the rules at x 60 / 120 / 180). The param_t `knob`
field holds the short name, or 0 to use the long one when it already fits.

The operator boxes
------------------
image 109708 B, RAM .data+.bss 30648 B, pool 73472 B. 40 bytes over the knob
legend, no RAM. 26 % / PK 32 % on the hardware, which is the same as before it
within the noise of reading the meter twice.

The boxes already redrew every 60 ms to brighten with level, so filling them
instead costs nothing new in the main loop. The patch each box blits grew from
(bw + 6) x (bh + 6) to (bw + 13) x (bh + 6) so that the feedback bracket is
inside it -- about 10 KB of pixels a second across all six, against the 520 KB
a second the spectrum screen moves. It is the cheapest of the three drawings.

The width is clamped to the column pitch, so a box can never blit over its
neighbour however tight the algorithm packs them. Algorithm 32, six carriers
abreast, is the worst case and tests/levels.txt holds it there.

Ratio, and the parameters that are hidden
-----------------------------------------
image 111260 B, RAM .data+.bss 30648 B, pool 73472 B. 1552 bytes over the
operator boxes, no RAM. The meter is untouched: none of this is in app_audio.

Most of those bytes are the ratio list, the two decade tables and the string
work to print "x4.50" and "3162HZ" without floating point. Forty of them are
the decade tables, which are two tables of ten rather than one of a hundred --
10^(f/100) factored as 10^(f/10) x 10^(f%10/100), both in Q12. That costs one
extra multiply and one rounding, worth 0.015 % against an exact table, and
saves 160 bytes.

Two things here are per-frame rather than per-edit and so worth watching. A
page is no longer an array that a bank indexes: page_at() walks the table
skipping what SHOW ALL is hiding, and it is called four times a frame to decide
what to draw and once more per knob that moved. The table is thirteen entries
long, so the walk is bounded at thirteen comparisons -- call it two hundred a
second, against the 520 000 pixels a second the spectrum moves. It does not
register.

The other is rat_index(), which finds where an operator sits in the list by
walking all thirty-seven entries and doing a multiply and a divide at each. It
runs once per frame for the bar under RATIO, and once per click. Also nothing,
but it is the one thing here that would grow if the list did, and the obvious
fix -- the list is sorted, so a binary search -- is not worth writing until the
list is long enough to need it.

The knobs on HOME
-----------------
image 111932 B, RAM .data+.bss 30664 B, pool 73472 B. 672 bytes over ratio, and
16 of RAM -- the twenty-byte buffer the voice line's message is built into,
rounded up. The meter is untouched again: nothing here is in app_audio.

A knob turned on HOME does exactly what a knob turned on a parameter page does
-- write one byte of the 156 and publish them -- plus build a short string and
hand it to say(). That is the same work the save prompt already did a letter at
a time. The legend is redrawn only when its key changes, which on HOME is the
set number, so stepping SEL costs one 240x16 blit and holding a knob costs none.

The span moving off KNOB1 and onto GLOBAL took the one special case out of the
knob loop, so HOME's two screens now run the same code. That is worth more than
the bytes it saved.

What it means
-------------
NV 8 was chosen to be safe and is nowhere near the limit; the headroom is better
spent on what the instrument is for (drawing envelopes, the algorithm, operator
levels) than on more voices. Step 4 spent some of it and cost nothing measurable.

Watch this number again after:
  - raising NV
  - raising CV_MAX / drawing more per frame (the UI steals memory bandwidth, and
    at some point the main loop stops keeping up even if the ISR does)
  - anything per-sample added to app_audio
  - DX_LG_N changed from 6 (smaller blocks cost more per sample)
  - anything that makes a knob detent do more than publish 156 bytes
  - say() being called from somewhere that repeats (it is cheap once, and the
    voice line redraws on every message)


ADSR
====

The envelope page gained a bank that says the DX7's eight envelope bytes as the four knobs every
other synth has, and a bank stopped being a fixed number of rows so that bank could be one row of
four cells instead of two rows of one.

  image   112112 B -> 112524 B   (+412)
  RAM     30664 B                (unchanged)
  cpu     unchanged

The +412 is the three bank helpers that replaced the stride arithmetic, the four-cell drawing, and
the four new parameter rows. There is no audio cost at all: ADSR writes the same eight bytes the raw
rows always wrote, and the engine never learns that anything changed. The drawing cost moved rather
than grew -- the graph is 104 pixels tall on the ADSR bank instead of 72, which is 7680 more pixels
to blit sixteen times a second, but the two parameter rows it replaced were 15360 pixels between
them. cpu_q8 does not see either, as ever; both are blit bandwidth, not audio.


FOCUS
=====

EDIT and ENV learned the difference between a tap and a hold. A hold is the page they always were; a
tap leaves HOME on the screen and lends that page's first rows to the four knobs. SHOW ALL came out
at the same time -- there is no longer a wall between the parameters worth reaching for and the rest,
because a tap reaches the first three without leaving the sound.

  image   112524 B -> 113232 B   (+708)
  RAM     30664 B                (unchanged)
  cpu     unchanged

Removing SHOW ALL gave back more than it looks: the adv flag was a byte on every one of the sixty-odd
parameter rows and a filter in front of every page lookup, so page_n and page_at went back to plain
indexing. The +708 is net of that -- the long-press timing, the two focus tables, focus_at, p_turn,
op_point, say_param and draw_home_title, less what SHOW ALL cost.

No audio cost. A focused knob turn goes through exactly the same p_turn as a knob turn on the page,
which is the reason it was factored out, and it publishes the same 156 bytes. Drawing is cheaper than
a page, not dearer: the title is 240x32 and the legend is already redrawn on any page change.

Watch this number again after:
  - the fourth EDIT cell gaining a WAVE parameter
  - LONG_MS being changed (400 ms is comfortably past a deliberate tap and comfortably
    short of a wait, but it has only been judged by one pair of hands)

ENVELOPES IN THE BOXES
----------------------
The operator boxes on HOME filled from the left already, and that fill was only ever worth anything
while a note was sounding. The gap was the screen you are actually looking at while you edit: nothing
playing, and six empty outlines. So the operator the knobs are on draws its envelope instead.

It gets the picture for free. eg_target() already folds the operator's output LEVEL into every
segment target -- which is why the ENVELOPE page's curve rises and falls as you turn LEVEL -- so the
same curve shows level and shape together with no new meaning invented, and the axes stop fighting
(x is time, y is level, exactly as on the page). The maths was pulled out of draw_eg into eg_shape(),
parametrised by width and hold, so the page and the thumbnail cannot drift apart.

  image   113232 B -> 114060 B   (+828)
  RAM     30664 B -> 30712 B     (+48)
  cpu     unchanged

The +48 is the cache: five x, five levels, and a checksum. A checksum rather than a dirty flag,
because `edit` is written from a dozen places and a checksum cannot go stale -- it is a hash of the
selected operator's twenty-one bytes plus the box width plus which operator it is. alg_eg_build()
runs at the top of both draw_alg and draw_alg_levels, and draw_alg_levels runs sixteen times a
second, so the check has to be the cheap path and the rebuild the rare one.

No audio cost at all: this is drawing. The rebuild itself walks eight envelope segments in integer
arithmetic and only happens on a knob turn or a voice load.

Only one box is ever a curve. The other five stay bars, which is what makes the curve read as "this
is the one you are editing" without a second cue -- and it is why the cost is five values and not
thirty.

Watch this number again after:
  - non-sine operators (the shape of the wave would want to show in the box too)
  - any new page that wants eg_shape() at a third size
