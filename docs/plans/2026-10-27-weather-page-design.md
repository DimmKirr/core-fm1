# Weather Page Design: WiFi Weather Display for FM-1

## Goal

Add a Weather page to the Felucca UI that connects to WiFi, geolocates via IP,
fetches current weather from open-meteo.com, and displays it with condition-colored
backgrounds and weather glyphs on the 240x240 LCD. The feature requires building
a proper lwIP-based networking stack first, replacing the hand-rolled TCP.

## Phases

1. **TCP/IP, HTTP, DNS stack** (lwIP `NO_SYS=1` integration)
2. **Weather page with glyphs** (UI component)
3. **Async weather fetcher** (non-blocking HTTP fetch pipeline)
4. **Reusable spinner primitive** (loading indicator for async pages)

## Phase 1: lwIP Network Stack

### What exists

- `wifi_tcp.c`: hand-rolled TCP server (raw packet construction, no retransmit)
- `wifi_lwip.c`: lwIP netif driver stub (frame I/O bridge)
- `CONFIG_WIFI_LWIP` Kconfig symbol (already defined)

### What to build

Replace `wifi_tcp.c` with lwIP 2.2.x in `NO_SYS=1` bare-metal mode.

**lwIP integration** (`wifi_lwip.c`, expanded):
- `netif` init: MAC address, `low_level_output()` -> WiFi TX path
- `netif->input()` fed from WiFi RX ISR/queue in main loop
- `sys_check_timeouts()` called from main loop (~15ms frame tick)
- DHCP client for IP address acquisition
- DNS resolver: `dns_gethostbyname()` (callback-based, built into lwIP)

**HTTP client** (`wifi_http.c`, new, ~200 lines):
- General-purpose async GET client on lwIP raw TCP API
- API:
  ```c
  typedef void (*http_done_cb)(int status, const uint8_t *body,
                               uint32_t len, void *ctx);
  static int  http_get(const char *host, const char *path,
                       http_done_cb cb, void *ctx);
  static void http_poll(void);  /* main loop */
  ```
- State machine: DNS_RESOLVE -> TCP_CONNECT -> SEND_REQUEST -> RECV_HEADERS -> RECV_BODY -> DONE
- Single concurrent request (sufficient for weather). Queue or reject if busy.
- Timeout: 10s per phase, total 30s max.
- Response buffer: static 2 KB (weather JSON is ~300 bytes).
- No chunked encoding, no TLS, no redirects (both APIs are plain HTTP).

**lwIP source**: BSD-licensed lwIP 2.2.x, vendored into `firmware/upstream/lwip/`
or as a git subtree. Only the `core/` and `include/` directories needed (~150 KB
source, compiles to ~40-60 KB depending on features enabled).

**lwipopts.h**: Minimal config for bare-metal weather client:
- `NO_SYS=1`, `LWIP_SOCKET=0`, `LWIP_NETCONN=0`
- `LWIP_DNS=1`, `LWIP_DHCP=1`, `LWIP_TCP=1`, `LWIP_UDP=1`
- `MEM_SIZE=4096`, `MEMP_NUM_TCP_PCB=2`, `PBUF_POOL_SIZE=8`
- `TCP_MSS=1400`, `TCP_SND_BUF=2*TCP_MSS`
- No IPv6, no IGMP, no PPP, no SNMP

### Main loop integration

```c
/* in core_fm1.c main loop, alongside usb_poll() */
#ifdef CONFIG_WIFI_LWIP
    wifi_lwip_poll();      /* feed RX packets to lwIP */
    sys_check_timeouts();  /* lwIP timers (DHCP, DNS, TCP retransmit) */
    http_poll();           /* HTTP client state machine */
#endif
```

## Phase 2: Weather Page with Glyphs

### Component placement

- UI module, conditional page gated by `CONFIG_WIFI`
- File: `firmware/src/ui/felucca/page_weather.c`
- Registered in `pages.c` under `#ifdef CONFIG_WIFI`
- Navigation: accessible via button combo or SYS menu (TBD by controls mapping)

### Layout (Felucca card + colored graph style)

```
┌──────┬──────┬──────┬──────┐
│ TEMP │HUMID │ WIND │ CODE │  <- 4 standard Felucca cards
│  22° │  65% │ 12kh │  CLR │
└──────┴──────┴──────┴──────┘
┌────────────────────────────┐
│  [condition-colored bg]    │  <- Y_GRAPH to Y_FOOT (126px tall)
│                            │
│    [32x32 weather glyph]   │  <- 1-bit glyph, rendered in white/theme
│       CLEAR SKY            │  <- condition text (AF_M)
│         22°C               │  <- large temp (AF_L or AF_M)
│    Istanbul, TR            │  <- city name (AF_S)
│                            │
│  Last: 14:30   WiFi: OK   │  <- status line (AF_S, dim)
└────────────────────────────┘
[ WEATHER    v0.1     WTHR  ]  <- standard Felucca footer
```

When fetching: spinner replaces the glyph area.
When offline: "NO WIFI" in dim text, cards show "---".

### Weather condition colors (RGB565)

Generated by a Python script (`tools/gen_weather_colors.py`), mapping WMO weather
codes to background colors. Grouped into ~10 categories:

| WMO codes | Condition | RGB565 hex | Approximate color |
|-----------|-----------|-----------|-------------------|
| 0 | Clear sky | `0x4C9A` | Sky blue |
| 1-3 | Partly cloudy | `0x6B9A` | Muted blue |
| 45, 48 | Fog | `0x8C51` | Gray |
| 51-57 | Drizzle | `0x5B6D` | Blue-gray |
| 61-67 | Rain | `0x3A4B` | Dark blue |
| 71-77 | Snow | `0xBDF7` | Light silver |
| 80-82 | Showers | `0x4A6B` | Storm blue |
| 85-86 | Snow showers | `0x9CF3` | Cool gray |
| 95-99 | Thunderstorm | `0x2945` | Dark slate |

Python generator script produces the C lookup table from WMO code -> RGB565.

### Weather glyphs (1-bit bitmaps)

8 condition glyphs, 32x32 pixels each, stored as `uint32_t[32]` arrays (1 bit/pixel,
128 bytes per glyph, ~1 KB total for 8 glyphs).

| Glyph | Used for WMO codes |
|-------|--------------------|
| SUN | 0 (clear) |
| PARTIAL_CLOUD | 1-3 (partly cloudy) |
| CLOUD | 45, 48 (fog/overcast) |
| DRIZZLE | 51-57 |
| RAIN | 61-67, 80-82 |
| SNOW | 71-77, 85-86 |
| THUNDER | 95-99 |
| UNKNOWN | fallback |

Generated by a Python script (`tools/gen_weather_glyphs.py`) that produces C arrays
from simple ASCII art or a small pixel grid definition. The glyphs are drawn with
`cv_rect` pixel-by-pixel (or a small `cv_bitmap_1bit` helper). License: original
work, GPL-3.0 (they're simple geometric shapes, not copied from any icon set).

Rendering helper in `weather_glyphs.h`:
```c
static void weather_glyph(int32_t x, int32_t y, uint32_t idx,
                          uint16_t fg, uint16_t bg);
```

## Phase 3: Async Weather Fetcher

### Module: `wifi_weather.c`

Non-blocking two-step fetch pipeline using the Phase 1 HTTP client.

**State machine:**
```
IDLE -> GEO_FETCH -> GEO_PARSE -> WEATHER_FETCH -> WEATHER_PARSE -> DONE
  ^                                                                   |
  └──────────────── (timer: 15-30 min) ──────────────────────────────┘
```

**API:**
```c
static void weather_init(void);        /* start first fetch when WiFi connects */
static void weather_poll(void);        /* main loop: drives state machine */
static int  weather_fetching(void);    /* 1 if fetch in progress */

/* cached result (read by page_weather.c) */
static const struct weather_data *weather_get(void);
```

**Data struct:**
```c
struct weather_data {
    int16_t  temp_c;          /* temperature x10 (e.g. 225 = 22.5°C) */
    uint8_t  humidity;        /* 0-100% */
    uint8_t  wmo_code;        /* WMO weather code 0-99 */
    uint16_t wind_kmh;        /* wind speed x10 */
    char     city[24];        /* from ip-api geolocation */
    char     country[4];      /* 2-letter code */
    uint32_t updated_ms;      /* fm1_ms timestamp of last successful fetch */
    uint8_t  valid;           /* 1 if data is populated */
};
```

**Flow:**
1. WiFi reaches `WIFI_STATE_CONNECTED`
2. `weather_init()` triggers first fetch
3. Step 1: `http_get("ip-api.com", "/json?fields=lat,lon,city,countryCode", geo_cb, NULL)`
4. `geo_cb` parses lat/lon/city, stores in static vars
5. Step 2: `http_get("api.open-meteo.com", "/v1/forecast?latitude=X&longitude=Y&current=temperature_2m,relative_humidity_2m,weather_code,wind_speed_10m", weather_cb, NULL)`
6. `weather_cb` parses JSON, populates `weather_data`
7. Timer resets: next fetch in 15 minutes

**JSON parsing:** Minimal key-value scanner (~80 lines). No full JSON parser needed:
scan for `"key":value` patterns for the ~6 fields we need. Numbers parsed with
a simple `atoi`-style function. No malloc, no recursion.

**Error handling:**
- HTTP error / timeout -> retry in 60s, max 3 retries, then wait 15 min
- WiFi disconnect -> pause fetcher, resume on reconnect
- ip-api rate limit (45/min) -> not a concern at 15-min intervals

## Phase 4: Reusable Spinner

### Location: `firmware/src/ui/felucca/draw.c`

Added to the Felucca drawing primitives alongside `fui_draw_head`, `fui_draw_card`,
`fui_draw_foot`.

**API:**
```c
static void fui_draw_spinner(int32_t x, int32_t y, uint32_t frame,
                             uint16_t color, uint16_t bg);
```

**Design:** Rotating arc or rotating dots (4-8 dots in a circle, one highlighted,
advancing every ~100ms based on `frame` tick). ~20 lines of code using `cv_rect`
for dot positions.

**Usage:** Any page doing async work:
- `page_weather.c`: during fetch
- `page_ble.c`: could use during scan (future enhancement)
- `page_files.c`: could use during USB enumeration (future)
