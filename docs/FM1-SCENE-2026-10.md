# FM-1 scene survey, early October 2026: what to integrate, what to borrow

Read-only survey, written 2026-10-05. This note is uncommitted. None of our repos were changed.

**How the survey was done:**
- GitHub: repo and code search, and the fork network of Felucca, SLOOP, Lunar Modulator, FM-1-RE, aroum and the emulator. Each fork was compared with its parent through the compare API.
- Issues and discussions of the main firmware repos.
- Web: Synth Anatomy, Piano & Synth, Sonicstate, groove-os.com, baudgirl.com.
- Reference clones, read-only, in `~/GitHub/refs/<name>`: Felucca, fm1-x0x, flowstate-fm1, chance-felucca, renebohne-sloop, renebohne-felucca, sloop-upstream, melodee-latest, jangada-upstream, lunar-modulator, lunar-modulator-looper, fm1-nes, Virtual-FM-1, FM-1-RE, fm1-custom-fw, fm1-emulator-upstream, mvave-fm1-open-firmware, fm1-workbench-public, fm1-firmware-patcher, fm1-dx7-patch-importer, fm1-polyseq.
- Scratch builds, from `git archive` copies outside the repo with our Docker toolchain:
  - Felucca 1.0.1 builds to **477,004 B**, the same size as its release `app.bin`.
  - X0X 0.9 builds to **580,068 B**.
- Both packages were also booted in our emulator (`fm1-emulator-boot` at `7a220f4`).

## 0. The short version

- **Felucca is back, and at 1.0.1** (`hugelton/Felucca`, re-created 2026-10-02; v1.0 2026-10-05, v1.0.1 2026-10-06).
  - The old handoff note said "that repo is gone". That is no longer true. Melodee is now a GitHub fork of it.
  - It has 13 engines: FM6 (an Apache-2.0 port of msfa), PHYS (DaisySP/Rings, MIT), NOISE, DRUM, SLICE and others.
  - Other new features: a piano roll, per-step chance, motion recording, spring reverb, a harmonizer, a modulation matrix, USB audio, TRS MIDI, web backup/restore and return to V15.
  - It all fits in **477 KB**.
  - Its build trick `size_fns.py` (LLVM `minsize` on UI code only) saves **8,068 B** [M]. That is more than twice our 3,812 B overflow.
- **X0X** (`charlesvestal/fm1-x0x`, GPL-3.0-only, Felucca-derived, 78 commits in 3 days) is the best-documented hardware bring-up so far.
  - **The CPU runs at 360 MHz**, read from the PLL registers on a real FM-1 [R]. Our old handoff note said ≤320.
  - Its other hardware lessons: encoder and LCD fixes, float divide-by-zero traps, a USB-audio clock that drifts against the host, and 512-frame audio halves.
- **SLOOP upstream** is still at 2.2 (`f2b44c2`), which we already contain [V].
  - Its forks: **Flowstate** (78 commits of "Musical Worlds", guardrails and an SDL simulator) and renebohne's played-notes LEDs and a visual FM UI.
- **The emulator upstream** is unchanged at `81b9ed9`.
  - Issue #1 (cliph, 2026-10-05) lists three gaps for Felucca 1.0. We already decode the two instruction forms; **we do not model USB EP4** [M]: Felucca 1.0.1 stops at `USB endpoint index exceeds modeled controller`.
  - X0X stops on the corex2 perf counter at `0x01EEE218` [M].
- **New hardware facts** (§3) change our CPU budget, emulator calibration, LCD speed and safety rules.

## 2. Per project

### Felucca: `hugelton/Felucca` (Leo Kuroshita / Hügelton)

| | |
|---|---|
| Licence | **GPL-3.0-only**, plus MIT / Apache-2.0 ports (`LICENSES/`) [V] |
| Last activity | v1.0.1 on 2026-10-06 (`20c275e`) |
| Activity | 201 stars, 20 forks |
| Tags | v0.8-beta, v0.9-beta, v1.0, v1.0.1 |

- **What is new since 0.9 (our base)**, in one 37 k-line commit `727f272`:
  - **Engines:** 13 engines. FM6 is an integer port of Dexed's msfa in `fm6_core.c` (Apache-2.0). It replaces DIGITAL, and old DIGITAL sounds convert. PHYS covers MODAL, STRNG, MEMB and sympathetic strings. NOISE covers colours, crackle, LFSR and metal. SLICE now has manual slices. DRUM is an 8-lane GM kit.
  - **Sequencer:** piano roll, drum grid, songs A–D, motion recording, per-step chance, divisions up to 4 bars, ARP REPEAT, chord keys with voicings.
  - **FX:** an FX hold layer (repeat, reverse, filter, tape stop, freeze, harmonizer), spring reverb, and a 4-slot modulation matrix per track with MIDI CC sources.
  - **UI and system:** on-device naming, 8 palettes, an Inter Tight anti-aliased font, Fukiai icons, USB audio input, TRS MIDI in with bend/sustain/clock, web backup/restore, sample recording and trim, return to V15.
  - **Tests:** about 30 new host tests.
- **v1.0.1:**
  - dim idle LEDs ("a short pulse riding on the 595 shift");
  - LEDS INV;
  - key LEDs follow the sequencer (#38);
  - QNT SEQ (#37).
- **Size:** image 477,004 B, RAM 88,884 B, pool 329,952 B [M].
  - Samples are 194,056 B ADPCM (5 sets). Ours are 315,854 B. That is where its headroom comes from.
  - The `minsize` pass is worth 8,068 B [M: `FELUCCA_SIZE=0` builds 485,072 B].
- **Relevance:** **integrate selectively** (§1 #1, #2/#3, #9, #10, #11).
  - It is the same licence and the same HAL family, so ports are cheap. But its project format, UI and engine list have diverged from SLOOP's.
  - SLOOP users already ask "are you going to implement the new things of Felucca 1.0?" (SLOOP #14 comment).
- **Community wishes**, from issues #39–#59 opened 2026-10-05:
  - parameter locks, macros/scenes, generative/mutation tools;
  - knob acceleration, a BPM lock, HOME as shift, temporary modifiers;
  - ratchets for notes, dry/wet FX with a phaser, FM6 per-operator editing;
  - Bluetooth MIDI (#17, still open).
- **Discussions:**
  - #43 asks for the X0X 606/808;
  - #4 asks for TRS MIDI (now in 1.0);
  - #36 reports a port named "Kartun Oscuro" and a lost connection after install (unexplained).

### X0X: `charlesvestal/fm1-x0x` (Charles Vestal)

| | |
|---|---|
| Licence | **GPL-3.0-only** [V] |
| Last activity | 0.9-beta on 2026-10-05 (`80b7d40`) |
| Origin | Fork of Felucca 0.x |
| Activity | 78 commits from 2026-10-03 to 10-05, 12 stars |
| Developed with | Claude Code, per its commit trailers |

- **What it is:** a ReBirth-style instrument:
  - 909 (from 9W9 / ER-99) and 808 (from 8W8);
  - two 303s (Open303 with Devilfish) with TB-3PO generators;
  - a break player (BB Gen, used by permission);
  - 16 patterns, polymeter, song mode, motion;
  - a master compressor with kick-keyed PUMP, a filter and a limiter;
  - USB audio input with a resampler, USB MIDI clock in/out;
  - help cards, undo by difference, autosave of changes only, a PERF test and an on-device load meter.
- **Size:** image 580,068 B, RAM 65,068 B, pool 316,272 B [M].
  - Per module [S]: 303 11,550 B, TB-3PO 1,427, 808 30,504, 909 256,386 (it holds hat and cymbal samples), FX 20,457, master 5,963, motion 1,290.
- **What is unique and valuable to us:** hardware measurements (§3) and the fixes they led to:
  - the encoder filter;
  - TIMER5 priority above ALNK0;
  - LCD SPI speed and dirty rectangles (the panel's TE output is not wired);
  - the float div0 trap;
  - the I2S clock against USB;
  - 512-frame halves;
  - the second-core start sequence from the SDK (it matches our `docs/DUAL-CORE.md`);
  - the `fm1_rescue.py` UBOOT restore.
- **Relevance:** **integrate** fixes and tools (§1 #2–#8, #14, #15, #17). **Inspire** on engines; an ACID engine is possible (§1 #12).
- **Licence caveats:**
  - `dsp/breaks*` is used **by permission** of BB Gen's author, and that repo has no licence. Do not copy it.
  - Open303 parts are MIT.
- **Our emulator:** it stops at `0x01EEE218` (perf counter MMIO), which is not modelled [M].
- **Open issue #1:** "digix0x as a better 303".

### Reverse engineering and tools

- **FM-1-transporter** (`kurogedelic`, MIT, 2026-10-01):

## 4. Top 10 recommendations

1. **Port Felucca 1.0's `minsize` UI build** (`size_fns.py` + `build.py` IR step).
   - It is −8 KB on Felucca [M] and very likely clears our 3.8 KB flash overflow without trimming samples.
   - Measure it on `feat/integration` first. Effort S.
2. **Fix the encoders:**
   - X0X's decoder (no two-scan filter, flick continuation);
   - Melodee's first-detent fix;
   - speed acceleration for continuous parameters.
   - Port the host encoder tests too.
   - These are the most-reported hardware bug across SLOOP and Felucca. Effort S.
3. **Correct our CPU assumptions:**
   - Write "360 MHz measured by X0X [R]; stock sets 240 [R]" into MEMORY-BUDGET.
   - Add a TIMER4-timed busy-loop readout to our hardware probe build so that **our** clock is measured on the first hardware session.
   - Calibrate the emulator's cycles-per-instruction against it. Effort S.
4. **Emulator: model USB EP4, the corex2 perf counters and the float div0 trap.**
   - Then Felucca 1.0.1 and X0X boot as regression firmwares, and the div0 class of hardware crash shows in the emulator.
   - Coordinate with cliph's patch (emulator issue #1) before the upstream PRs. Effort S–M.
5. **Raise the LCD SPI to 30 MHz** (BAUD 1), then consider dirty-rectangle sends.
   - It frees main-loop time and removes tearing.
   - Hardware test needed; X0X runs 60 MHz [R]. Effort S.
6. **Audit for divide-by-zero**: integer divisors in the UI, clock, tempo and the adaptive tracker. Our HAL traps div0 and a trap means a crash on hardware. Optionally clear the trap as X0X did. Effort S.
7. **USB audio clocking:**
   - Test `feat/usb-audio` under live monitoring against a drifting I2S (~44.15 kHz).
   - If packet-size feedback drops out as X0X reports, adopt X0X's resampler (`80b7d40` + `uac_test.c`). Effort M.
8. **Safety kit for the hardware phase:**
   - adopt X0X's `fm1_rescue.py` (macOS, UBOOT, hash-checked V15, changed sectors only);
   - adopt Felucca 1.0's web **full backup/restore** and **return to V15**;
   - give Optimist its own package identity (not `FM-1_900`).
   - Effort M.
9. **Cheap Felucca 1.0 / fork features as builder switches:**
   - per-step chance;
   - keys light the sequenced/played notes (renebohne `e2e5099`);
   - QNT SEQ;
   - spring reverb;
   - BASS+ speaker mode;
   - screen brightness;
   - delay-halving when the line is short.
   - Each is a few hundred bytes. Effort S each.
10. **Next-round candidates, with the builder:**
    - **motion recording** (~1.5 KB [S], buffer in the pool);
    - **PHYS** (~6 KB [S] + 51.5 KB pool [S]; reduced builds only);
    - an **ACID** engine from X0X (303 + TB-3PO, ~13 KB [S], CPU-heavy).

### 5.2 What changed

**What a World is.** One JSON file (`format: "flowstate-world/1"`) that describes a complete playable piece for SLOOP's four tracks [V `docs/worlds.md`]:
- metadata: name, category, blurb, tempo range, key and scale, swing;
- four tracks: role, engine, factory preset by name, parameter values by label, drum kit;
- patterns in a text notation: chord tokens `c1`..`c9`, degrees, accents, slides and ties, drum lanes as `x.s.g` strings;
- progressions in Roman numerals;
- scenes A–D: progression, ENERGY table, transition, fill, parameter and FX overrides;
- up to 8 variations: preset swaps, pattern swaps, parameters, an ENERGY bias, macro defaults;
- four macros (COLOR, MOTION, SPACE, ENERGY): up to 40 mappings with curves and smoothing, and up to 8 cross-macro rules;
- ENERGY bands that add layers, drum lanes, density, fills and ratchets as one knob turns;
- Smart Keys: white keys play the melody scale, black keys the current chord's tones;
- a guard block: note ranges, polyphony, parameter ranges, arrangement timing, a CPU cap.

**Storage** [V `docs/design/fwd1-format.md`]:
- `tools/worldc.py` compiles a World to an **FWD1 blob**: little-endian, byte-aligned, a 24-byte header with magic, version, flags, length, an FNV-1a id and a CRC-32, then up to 16 typed sections. Factory blobs are capped at 3,072 B, user blobs at 3,840 B.
- The firmware validates each blob byte by byte (`wb_check`) and never casts it to a struct.
- Factory Worlds are compiled into the app image by `tools/gen_worlds.py` (`build/gen/felucca_worlds.h`). A World that fails `worldc check` fails the build.
- User Worlds ("MY WORLDS", 10 slots) are whole blobs with a USER flag plus an OVERRIDES section of `{scope, id, value}` records. They live in flash `0xE5000`–`0xFBFFF` (`docs/hardware-calibration.md` §3.2).

**The factory library** (Phase 18, `docs/worlds.md` §19, `docs/progress.md` 1150–1313) [R, figures from their logs]:

- **Blobs: 1,034–1,801 B, 39,276 B in all**; 39,564 B in the image with alignment and index, against a budget of 42,296 B.

### K.2 Findings, ranked

1. **Stock V15 is now Apache-2.0, and the kit's copy is byte-identical to ours.** `sha256(sdk/firmware/FM-1_015.fwsc) = db1642b2…edb8a` = O:`tools/fm1_rescue.py:57` `STOCK_SHA256` = O:`web/fm1pkg.js:32`. So Optimist may host and bundle the official V15 image (with the Apache-2.0 text and M-VAVE's attribution). Today the installer tells the user to download it (O:`web/installer/installer.js:93-94`, "Download FM-1 V15 from …") and `fm1_rescue.py` needs the file passed in. Port: one hash-pinned `FM-1_015.fwsc` on Pages/release, a "Back to V15" button with no download step, and `fm1_rescue.py` defaulting to it. Effort small; zero firmware cost. **Usable.**
2. **Restore the four factory voice banks after a return to V15.** K:`sdk/WebUpdate.js:93-101` pulls the stock `USR` entry (73,226 B, first 16 KiB = four voice banks) out of the hash-pinned V15 package, and K:`WebUpdate.js:376-400` writes it back to a running V15 with stock SysEx commands 33 (erase a 4 KiB bank, `[5,0,bank>>8,0,0]`) and 34 (512-byte write). Our return to stock warns that V15 does not use our data (O:`installer.js:65,74`) but leaves whatever Optimist wrote where V15 keeps its voices. Port the routine into O:`web/fm1ota.js` / the installer. Effort small-medium (test against a real V15). **Usable** (GPL JS; the command numbers are facts).
3. **The audio interrupt: render aside, commit only a half the DMA still owns** (K:`app/board/audio.c:27-64`, `fm1_audio.h:30-36`). M-VAVE renders into a separate buffer, then with interrupts masked (`icfg` bit 8) copies it into the free half **only if** the half is still free before and after and the time used is under 7/8 of a block; otherwise it counts an overrun and leaves the half alone. It also rejects interrupts that arrive too early or too late (`interval` outside ±1/8 of a block, lines 35-40). Optimist renders straight into the DMA half (O:`firmware/src/core/audio.c:149-164`) and only notices afterwards that the DMA moved (`late`, line 169), so a late half is played half-old/half-new (a click) rather than a clean repeat. Port cost: one 2 KiB buffer (256 frames x 2 x 4 B) and a ~5 µs copy per half, or keep in-place rendering but skip `fm1_audio_ack_half` when late. Effort small. **Usable.** Not a SIMD fix (SIMD crackles with no late half, see the doc comment in O:`firmware/hal/fm1_simd.h:13-15`).
4. **Interrupts stay enabled inside the audio ISR on the real chip (inferred from M-VAVE's code).** M-VAVE masks `icfg` bit 8 around its copy inside the audio ISR (K:`fm1_audio.h:37-48`, `audio.c:48-54`), which only makes sense if the core keeps the global enable through interrupt entry. That is the open question in O:`core/audio.c:141-143` ("not measured on the FM-1; the emulator's model clears it"). If true, TIMER5 (priority 4, O:`system/main.c:97-109`) does nest into the render on hardware and never in the emulator. Our wrappers save only `psr, rets, reti, r0-r3` (O:`firmware/hal/fm1_isr.S:10-16`) and rely on the C ABI for the rest; any core state outside that set (multiply-accumulate or SIMD-related state, if the core has any) would be corrupted only on hardware. This is a hypothesis for the "clean in emulator, crackles on hardware" class, not a measured cause. Cheap test: a SIMD=1 build with `dualcfg flat` (TIMER5 at 3, no nesting, O:`main.c:106`); if the crackle stops, nesting is the cause. M-VAVE's ISRs are compiler-generated `interrupt("")` handlers in RAM (`.volatile_ram_code`, K:`sdk/include/fm1.h:16`), and their 10 kHz scan ISR is tiny (see 5).
5. **Key-matrix scan by SPI2 + DMA instead of bit-banging the 74HC595** (K:`app/board/fm1_input.h:34-56, 112-131, 145`). The column word goes out through SPI2 (`0x11E00`, routed by IOMAP `0x51020` bit 17, divider 29) as a 2-byte DMA; the 10 kHz ISR only reads the rows, latches, and queues the next column, with a stall watchdog (20 ticks) that resets SPI2. Optimist shifts 16 bits by hand with three read-modify-write SFR accesses per bit in the same 10 kHz ISR (O:`firmware/hal/fm1_input.h:147-168`), an ISR that nests into the audio render (item 4). Estimated saving a few % of CPU0 *est.* (not measured); also shortens the nesting window. Debounce constants are the same as ours (press 2, release 8, encoder rest relearn after 900 frames: K:`fm1_input.h:80-83,101-102` vs O:`fm1_input.h:48,242-243`). Our LIGHTS dim pulses ride on the bit-banged shift (O:`fm1_input.h:105-119`) and need a rework if the shift moves to DMA. Effort medium. **Usable.**
6. **ST7789 panel tuning.** M-VAVE sends the full vendor set: porch `B2`, gate `B7=56`, VCOM `BB=18`, `C0=2C`, `C2=01`, `C3=1F`, `C4=20`, `C6=0F` (60 Hz), power `D0=A6 A1`, both gamma tables `E0/E1`, then `36=00`, `3A=55`, `E7=00`, `51=FF`, `21` (K:`app/board/lcd.inc:75-84`). Optimist sends only reset, sleep-out, `3A`, `36`, `21`, `13` and says "voltage and gamma stay at the defaults" (O:`firmware/src/display/lcd.c:105-117`). Their gamma/VCOM may be what the stock look is tuned to. Effort tiny (about 50 B of flash); check on the panel by eye. **Usable.**
7. **28 KiB of extra RAM: M-VAVE ships with 7 of 8 D-cache ways given back as RAM** (`FREE_DACHE_WAY = 7`, `cache_ram` at `0x1F20000+`, K:`sdk/config/linker.ld.in:18-28,378-396`). Optimist's `app.ld` has no cache-RAM region (O:`firmware/app.ld:13-20`); the idea is already in O:`docs/SPEED-IDEAS-sloop.md:131`. The kit confirms the configuration runs in a shipping FM-1 firmware that reads samples through XIP. We bring the chip up without the SDK, so the cache-way register setup must be found and done in `crt0.S`. Effort medium; value high where "the RAM is full". **Reference only** (the linker file's licence is mixed), the fact is free to use.
8. **Per-track microtuning** (K:`app/instrument.h:54-75`, implementation K:`web/engine/sound.c:284-302, 379`; project block `FM1T` K:`instrument.h:169-173`). Twelve cent offsets per track (-127..+127) by pitch class, plus an "alt" table for steps flagged with bit 13 or a held key, read at note-on. Optimist has a TUNE in cents per part (O:`core/voice.c:1321`) and no per-pitch-class tables (grep). Cost about 200 B RAM (8 x 24) and a table lookup per note-on. Effort small-medium (storage TLV + a page). **Usable.**
9. **Atomic flash records with a commit word** (K:`app/project.c:12-21, 409-419`, tuning journal `:155-217`): write the record with `commit = 0xFFFFFFFF`, verify, then program `commit = 0`. Optimist already has an A/B scheme with the header written last (O:`firmware/src/storage/storage.c:5-8,304`). Nothing to port; noted as a check that ours is equivalent.
10. **Packager, `Package.cs` (MIT)**: the same flash.bin / ufw layout as O:`tools/fm1pkg_make.py` (CRC16 0x1021, ENC cipher, key `0x980F`, 0x4000 app area, the product marker after each 47-byte block, K:`Package.cs:126-134`), with a VM/BTIF/USER layout of its own (USER 536,576 B ending at `0xFF000`). (b) The kit's files are explicitly Apache-2.0, so the cloud build could vendor `uboot.boot` and `cfg_tool.bin` (identical to ours) from the kit instead of fetching gitee (`toolchain.py:39`). Effort small. **Usable.**
11. **M-VAVE's own update loader `ota.bin`** (19,969 B, sha256 `ef1f2db8…`, identity `ota-FM-1_015` per K:`WebUpdate.js:148-149`) is now Apache-2.0. Our installer already accepts it only for writing V15 (O:`web/fm1ota.js:15-20`). Not needed for our packages; a legal fallback loader if ours ever breaks. **Usable.**
12. **Identity space.** The official open builds use `FM-1_8` + six digits (K:`Package.cs:138`, `app/version.h:6`). Our `FM-1_7\d\d` (O:`tools/flash.py:26`) does not collide with it; it still collides with Skiff `FM-1_711` and Fart Machine One `FM-1_701` (§9.4).
13. **Update protocol hardening worth copying into the installer** (K:`WebUpdate.js:286-330, 415-445`): an "arm" command carrying the package's SHA-256 build id before writing, and after the reboot a capability read-back that must report that same build id; a bounded re-send of the finish acknowledgement; a single Web-MIDI port pair (`AMBIGUOUS` refused). Our firmware would need a capability reply with its build hash. Effort small-medium. **Usable.**
14. **Transfer protocol niceties** (K:`app/transfer.c:8-14, 234-240`): every reply is cached and an exact retry gets the cached reply, so a lost reply never repeats a write; one request at a time; replies sized for a 128-byte queue. Our editor protocol could adopt the idempotent retry. It also accepts DX7 single-voice SysEx straight into a track (`:253-264`; Optimist has DX7 SysEx already, O:`io/usb/usb.c:636`), and MMC transport (`:249-251`; not found in Optimist by grep). **Usable.**
15. **SEA sample codec** (K:`web/synth/sea_decode.c`, `sea_encode.h`, `sdk/include/fm1_sea.h:7-27`): 5 or 6 bits a sample, 320-frame chunks of 228 B at 5 bits (5.7 bits/sample with headers), LMS predictor, 32 kHz in their sample bank (K:`sdk/Samples.js:4`). Optimist uses 4-bit IMA ADPCM (O:`engines/sample/eng_sample.c:12`): smaller, worse. SEA would be a quality option that costs about 40 % more flash per second and a heavier decode (4-tap LMS per sample). The native decoder is in the closed library; the open one is the browser decoder (portable C). Effort medium. **Usable** (MIT).
16. **PSG engine** (K:`web/synth/psg.c` GPL adapter + K:`third_party/synth/emu2149.c` MIT): three emulated AY/YM chips for 8 voices, modes YM/AY/NOISE/MIX, shared noise per chip. Optimist has no PSG (grep). Flash about 6-8 KB *est.* (emu2149 is 637 lines with volume tables); CPU modest (integer). Effort medium. **Usable.**
17. **Pluck** (K:`third_party/synth/pluck.c`, MIT, DaisySP String): fractional-delay Karplus-Strong in float. Optimist's PHYS already covers it (O:`engines/phys/`). Skip.
18. **Shared FX** (K:`web/engine/effects.c`): four combs and a 2048-sample delay, the "16 FX demos" are demo projects. Optimist's FX are far ahead. Skip.
19. **Mixing USB / Bluetooth audio** (K:`app/audio_output.c:15-40`): master gain slewed 8/127 per block (no zipper), USB playback added before clipping, Bluetooth after, the block dropped if USB changed stream during the copy (`-2`). Our USB audio is our own (O:`io/usb/usb_audio*.c`); the -2 "stream changed during copy → silence the block" rule is the only idea. **Usable.**

### K.4 The 303 (kit `third_party/synth/bass303.c` against O:`firmware/src/engines/acid/bass303.c`)

Licence: `third_party/synth/bass303.c/.h`, `bass303_state.h`, `dsp_math.h`, `fixed.h` MIT; `app/synth/bass303.h`, `web/synth/voices.c`, `web/engine/*.c` GPL-3.0-only WITH the exception: all usable. **Provenance (inferred):** the kit's MIT `bass303.c` has X0X's exact parameter table and defaults (VOLUME 96, which O:`engines/acid/bass303.h:43-56` records as X0X's own change from schwung-303's 102), X0X's soft-drive constants (0.15 / 0.148885) and its 2x polyBLEP/tanh structure: it looks derived from X0X (GPL-3.0), not fresh from Open303. No problem inside a GPL project, but do not relicense any of it as MIT.

The kit's sequencer cannot slide between two different notes: it releases the held note before the next note-on (K:`web/engine/sequencer.c:207-229`), so the slide test in K:`web/synth/voices.c:103` never fires from the sequencer; accent is only velocity >= 100. Found while comparing (verified by reading, not run):
- **RAT is unreachable in Optimist.** O:`engines/acid/acid_dsp.c:25-28` maps our 8 EDIT values to CUT RESO ENV DEC ACC WAVE DRV SLD; nothing sets the drive type, so the dm-Rat code is dead flash. Either expose it or drop it from the build.
- **Accent may stick across a slide.** O:`core/voice.c:694-697`: on a legato note the voice's velocity is only ever raised (`if (vel > v->vel ...)`), and `acid_legato` treats velocity >= 120 as accent (O:`engines/acid/eng_acid.c:46-51`), so an unaccented step slid to from an accented one probably keeps the accent. Needs a host test.

Portable, ranked: (1) fix the sticky accent (own code, XS); (2) expose ACC DECAY (fixed at 194 ms today) and DRIVE TYPE on a third page, the kit's three-page FILTER / OSC-LEVEL / DRIVE-SLIDE layout (K:`app/screen.c:888`) as the model (S-M, about 0 flash); (3) pitch bend and microtuning into the 303 like the kit's `pitch_target` (K:`bass303.c:22-25, 75-77`, MIT, S; O:`eng_acid.c:17-18` says none reaches ACID today); (4) with RAT exposed, the kit's longer release while RAT is on (6 / 60 ms, K:78) against a click (MIT, XS); (5) the kit's 1x "RAT" as a cheap drive for the CPU guard's lite mode (MIT, S, aliases). ### K.5 The FM engine and its editor (kit `web/synth/dx7*` against O:`firmware/src/engines/fm6/`)

Licence: `dx7core/env/lfo/pitchenv/ctrl.*` and `dx7note.*` Apache-2.0 (Google MSFA; `dx7note` adds Pascal Gauthier's Dexed copyright); `dx7synth.*`, `dx7math.*`, `synth_dx7.h`, `voices.c`, `mixer.c`, `fixed.c`, `demo_bank.h`, `app/fm_patch.h`, `app/presets.c` GPL-3.0-only WITH the exception. All usable. `dx7math.c`'s `dx7_sin_log_table` / `dx7_sin_exp_table` (:893, :960) are Dexed's Mark I tables under a GPL tag; we generate the same ones (O:`tools/gen_tables.py`), so we need not take M-VAVE's copy. No DX7 ROM voices anywhere: the kit's 16 FM programs are built in code from M-VAVE's own operator-pair recipes (K:`app/presets.c:89-185`), and `demo_bank.h` holds 8 formant-synthesised vocal drum samples, not FM patches (K:`demo_bank.h:12-40`).

Verdict: both engines descend from MSFA/Dexed; the kit's open C is about Dexed's "Mark I" path, and FM6 already does all of it and more.
- **Coverage:** both keep the full 155-byte VCED (6 operators, 32 algorithms, EG rates/levels, keyboard level and rate scaling, feedback, transpose, fixed/ratio, detune, pitch EG, LFO with PMS/AMS/delay/sync/6 waves) (K:`app/instrument.h:129`, `app/screen.c:157-172`; O:`eng_fm6.c:45-52`). The kit adds a per-track ADSR overlay and an operator mute mask (K:`instrument.h:134-141`). FM6 adds the DX7 function block (bend, portamento/glissando, wheel/foot/breath/aftertouch) and three resolutions MODERN / MARK I / OPL (O:`eng_fm6.c:48-52, 783-795`).
- **.syx:** the kit's device takes one 163-byte single voice on the track's channel (K:`app/transfer.c:253-265`); its workbench reads voices and 4,104-byte banks and exports voices (K:`sdk/WebUpdate.js:481-518`). FM6 handles voice, 32-voice bank to flash, parameter change, function parameters and dump requests (O:`engines/fm6/fm6_store.c:8-19`), and our editor imports/exports voices and banks with a library (O:`web/editor.html:1575-1592, 3774-3855`). We are ahead.
- **Arithmetic:** kit 14-bit EG gain (`ENV_MAX = 1<<14`, K:`dx7core.c:10`), Mark I operator (two 1024-entry u16 lookups, no multiply, K:`dx7math.c:1048`), gain interpolated per sample in the log domain (K:`dx7core.c:176-245`), Q24 1025-entry frequency table, 64-sample control blocks, 8 voices a DX7 track (K:`web/engine/sound.c:221, 799`). FM6: MODERN (1025-entry Q24 sine, interpolated, 64-bit gain multiply), MARK I (the kit's method), OPL; asm loops for MODERN and MARK I (O:`eng_fm6.c:291, 330-335, 806, 840-860`); about 31 KB flash and 10.5 KB RAM (O:`tools/builder/costs.json`).
- **Sound:** feedback identical (two-sample average, 2- and 3-operator loops for algorithms 4 and 6, +2 shift for 4, 6, 32: K:`dx7core.c:71-170, 263-311` / O:`eng_fm6.c:1005-1040`). The kit's EG is plain MSFA without Dexed's static segment times; FM6 has the equal-level hold and the level-0 attack delay (O:`eng_fm6.c:557-563`) and a Dexed parity test (O:`tests/fm6_parity.sh`, `tests/dexed_ref.cc`), so held segments and slow starts are right on FM6 and wrong on the kit. Neither oversamples. The kit sums with saturation into a Q24 bus with a DC blocker and a poly/mono fade (K:`dx7synth.c:526-611`); FM6 clamps a voice at 16 unit sines as Dexed does (O:`eng_fm6.c:1498`).

Portable, ranked: (1) **per-track 12-note microtuning with main and alt tables** (same as K.2 #8; for FM6 one add of `cents * 2^24 / 1200` to the operator base pitch at note-on, O:`eng_fm6.c:491, 1125`; kit K:`dx7note.c:100`, `web/engine/sound.c:284-310, 379`; usable, small for FM6, medium for all engines plus project, SCL page and editor; 24 B a track, under 1 KB flash *est.*); (2) **envelope shape preview** in the web editor, a static drawing of rates/levels with stage markers and an L3 hold, labelled as not a time trace (K:`app/screen.c:751-768`; usable; small in JS on the FM6 operator rows, O:`web/editor.html:3123`; it is a picture of parameters, not a meter, so it fits "editor, not a DAW"); (3) **algorithm diagram in the web editor** with switched-off operators marked (port our own `ui/sloop/ui_fm6.c:339`; kit K:`screen.c:2857` as reference); (4) optionally the kit's 16 recipe patches as extra ROM voices (usable, about 2 KB, low value: simple pair stacks on algorithm 5). Reference only: the poly/mono fade and DC blocker (would break Dexed parity), the kit's quick page (ALG, FB, TRANSPOSE, level; our OPERATOR row covers it). Not usable: the device asm kernels.

### K.6 The workbench and simulator (K:`sdk/Update.html.in`, `Simulator.js`, `Samples.js`, `web/engine/*`)

One page carries everything: the whole instrument compiled to WebAssembly (WASI SDK 27, `tools/Build-Web.ps1`) and played by an AudioWorklet (K:`Simulator.js:8-195`), a virtual panel, the firmware updater, project and voice library, and a ten-chapter manual. The device's own `screen.c` is built into the simulator and publishes up to 32 clickable regions per page with a label and a value (`web_target`, K:`app/screen.c:2660-2700`), so clicking a value on the simulated LCD opens an editor for it ("LCD 参数编辑"). Samples are encoded in the browser to SEA5 at 32 kHz into a 456 KiB bank of 8 slots (K:`Samples.js:4-30`). The page compares a device snapshot with the local copy (K:`Simulator.js:220-238`).

For Optimist: the simulator is the "try it in the browser" idea (our emulator and builder are separate tools); it carries a meter and transport, which our editor rule excludes, so only the parts that edit are candidates: (a) the clickable-LCD mapping for a future screen mirror in the editor, (b) the device-vs-local snapshot compare before a write, (c) the in-browser sample encoder (we have `tools/fm1_sample_upload.py`; the editor could encode IMA in JS). Effort medium each; **usable** (GPL-3.0-only with the exception).

### K.7 Caveats

- Nothing in the kit was built, run or measured. Costs marked *est.* are guesses from source size. The DX7 and 303 comparisons were made by two read-only helper passes and spot-checked here (the RAT mapping, the legato velocity line, `synth.json`, FM6's static segment times); the sticky-accent and aliasing statements are inferences from code.
- The "interrupts stay enabled in the ISR" point (K.2 #4) is an inference from M-VAVE masking `icfg` bit 8 inside its ISR, not a hardware measurement, and the nesting hypothesis for the hardware-only crackles is untested.
- The `uboot.boot` comparison decrypted only the V15 entry table (with O:`tools/fm1_install.py`'s `logical_image`), not the SPL itself.
- `libfm1_engine.a` was not opened; nothing here comes from it.
